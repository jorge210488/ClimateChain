# Stage 08 - Data Pipeline and Model Training

## Scope completed

- **Objective achieved:** The pricing model is now trained from thirty years
  of observed daily rainfall for every region the service knows, by a script
  that reproduces the committed artifact byte for byte from a committed,
  checksummed dataset. The artifact records its provenance — dataset version
  and checksum, source, split, configuration hash, and the hash of the trainer
  itself — and the runtime reports that provenance on readiness. The synthetic
  Stage 07 model is archived and scored on the same held-out years, so the
  improvement is a measured comparison rather than a claim.
- **Purpose and value:** Stage 07 proved the service could load and serve a
  model; it could not claim the model priced real risk, because the data behind
  it was drawn from a distribution somebody chose. This stage replaces the
  evidence behind the coefficients without touching the artifact contract or
  the serving code, and does it in a way an auditor can rerun: dataset in the
  repository, training deterministic, metrics regenerated by the gate. The
  time-based evaluation is what makes the number honest — the model is scored
  on 2019-2024, which it never saw, and the synthetic model turns out to have
  under-priced that period by more than four times.
- **Functional result:** `python scripts/train_rainfall_model.py` retrains
  `baseline-premium-v3` from `data/rainfall-history.json` in a few seconds
  and produces the committed artifact and metrics file unchanged.
  `GET /health/ready` now reports `datasetVersion`, `trainingKind`, and
  `transitional` alongside the model version and checksum. `POST /predict`
  prices from the observed model with no change to the request contract and
  one additive response field, `extrapolated`. `python scripts/stage8_check.py`
  is the gate: lint, format, dataset integrity, retrain-and-diff for artifact
  and metrics in a mode that writes nothing, 284 tests, and a real process
  boot. Deployed profiles refuse to start on anything but an observed,
  non-transitional artifact.
- **Integrated previous-stage outputs:** The Stage 07 runtime is consumed
  unchanged as the evaluator — `app/models/baseline.assess_risk` scores both
  the new and the archived model on the holdout, so the metrics describe the
  deployed code path. The Stage 07 artifact loader validates every artifact
  the trainer writes, and the Stage 07 gate (`stage7_check.py`) still runs as
  a subset. The backend's `docs/api/backend-openapi.json` (Stage 05) and
  `policy.constants.ts` (Stage 05/06) continue to be read by the contract
  tests; the shared pricing vectors (`shared/contracts/`) still pass on both
  sides. The backend's chain-free gate was rerun after the change to confirm
  nothing on the consumer side moved.
- **Runtime data sources (real vs test-only):** Real — the model artifact,
  now trained on ERA5 reanalysis (assimilated observations at ~10 km, served
  as daily precipitation sums by the Open-Meteo Historical Weather API,
  CC BY 4.0). The artifact is tagged `kind: "observed"`,
  `transitional: false`, and the gate refuses an artifact that says otherwise.
  Test-only — nothing; the tests exercise the committed dataset and the
  committed artifact. No runtime path reaches the network: the fetch is a
  deliberate, separately-run script.
- Retained from Stage 07 by design: the artifact schema version and feature
  names, the 0.35 premium loading, the eight regions, and the premium floor.
  What changed is the data, the evaluation, and — after the second review
  round — the meaning of `regionRisk`: a fitted per-region effect in log-odds
  rather than mean rainfall. The runtime evaluates it identically.

## Decisions made

- **Source: Open-Meteo's ERA5 archive, not a keyed provider.** It is open,
  keyless, licensed for this use, and serves a reanalysis product that is
  observationally constrained at every grid point — including the regions in
  Latin America where station records are sparse or paywalled. The
  `WEATHER_API_*` variables stay declared and empty for a provider that is
  not. Choosing a keyed provider would have made the pipeline depend on a
  credential the repository's policy says not to commit, for no gain in data
  quality at this resolution.
- **The dataset is committed, not fetched by the gate.** 351 KB is a small
  price for a gate that cannot fail on a remote service's availability, and
  for a training run an auditor can repeat without an account. The fetch is
  a separate, deliberate act, and a refresh that returns identical data
  leaves the file byte-identical so `git status` reports real change only.
- **Split by calendar, not at random.** Windows overlap in time; a random
  split of windows would leak the holdout's weather into training and
  flatter the model. Fitting on 1995-2018 and scoring on 2019-2024 is the
  test a deployed model actually faces: pricing years it has not seen.
- **Non-overlapping windows.** Trigger frequency is measured on windows tiled
  end to end, not slid one day at a time. Sliding windows would count the
  same storm dozens of times and make the sample look far larger than it is.
- **Region risk is measured on the training period only.** Using the full
  series would let the holdout years inform a feature the holdout is then
  scored on.
- **The runtime's evaluator scores the holdout.** `assess_risk` is the code
  that prices; scoring with it means the metrics describe the deployed path
  rather than a re-implementation that could drift from it.
- **Proper scoring rules, and the previous model on the same holdout.** Log-
  loss and Brier are what a probability forecast should be judged on. The
  archived synthetic artifact is scored on identical windows, which is the
  only way "better" means anything; that is why it is kept in the repository
  rather than deleted.
- **The configuration hash covers the trainer itself.** `configHash` includes
  the SHA-256 of `train_rainfall_model.py`, so a change to the fitting code
  changes the artifact even when the numbers happen to survive it. Reformatting
  the trainer during this stage changed the artifact checksum for exactly
  that reason, and the gate caught it.
- **Provenance is additive and optional in the loader.** The Stage 07
  runtime loads the new artifact without modification, and the archived
  artifact without a `training` block still loads. The gate — not the loader
  — is what insists the *current* artifact be observed and non-transitional,
  because an operator may legitimately need to load an old artifact during an
  incident.
- **The loading stays at 0.35 and is not estimated.** It is a commercial
  margin; the data cannot decide it, and dressing it up as a fitted parameter
  would misrepresent a choice as a finding.
- **Model family unchanged.** A more expressive model was not attempted.
  With eight regions and one feature per axis, the honest claim available
  from this data is calibration on the holdout, and the linear log-odds model
  delivers it (predicted trigger rate 0.101 against observed 0.097). A richer
  model belongs to a stage with more regions and a reason to need it.

## Review round

An external review of the stage produced eleven findings. Each was checked
against the code before deciding; the ones that named a real defect or a gap
in the stage's own guarantees were fixed, the ones that describe later-stage
work or trade a stated policy for a different one were declined with the
reason recorded here.

### Fixed

- **P0 — the local `.env` still pointed at the archived v1 artifact.** True,
  and invisible to the gate by design: the gate and the tests isolate
  themselves from a developer's untracked `.env`, and this developer's file
  predated the move. Fixed locally; `.env.example` and the config default were
  already correct, so a fresh clone was never affected. No code change — a
  gate that read the local `.env` would stop being a gate.
- **P1 — a deployed profile accepted the synthetic model.** Fixed. `staging`,
  `testnet`, and `production` now refuse at startup any artifact that is not
  `kind: "observed", transitional: false`, including one with no provenance at
  all. The single override is `MODEL_ALLOW_TRANSITIONAL=true`, off by default,
  logged as a warning at startup, and readiness keeps reporting the real
  provenance while it is on. Development and test load anything, which is how
  the archived artifact stays testable. Ten tests cover the three profiles,
  the override, and the no-claim case.
- **P1 — the fetcher accepted booleans, NaN, and a shifted calendar, and
  overwrote the dataset before validating it.** All confirmed and fixed.
  `parse_series` now refuses, value by value, anything that is not a finite
  non-negative number, and requires `daily.time` to equal the exact UTC
  calendar requested. `write_dataset` writes to a sibling temporary file,
  fsyncs, reads it back through the trainer's own loader, and only then
  replaces the old file atomically; a fetch that produced something unloadable
  leaves the committed dataset untouched. Fourteen tests, none touching the
  network.
- **P1 — the configuration hash covered raw trainer bytes, so a CRLF checkout
  would change the artifact.** Confirmed. The fingerprint now normalises line
  endings before digesting, and `.gitattributes` pins LF for `*.py` as well.
  The NumPy half of the finding is addressed by evidence rather than a lock:
  coefficients are rounded to twelve decimals before they are written, and
  the artifact is byte-identical between the local toolchain (Python 3.13,
  NumPy 2.5.2) and CI (Python 3.11, NumPy 2.4.6). A lockfile arrives with the
  Stage 12 container build, per the repository's dependency policy.
- **P2 — provenance could look valid while incomplete.** Fixed. A `training`
  block must carry `kind` (one of `observed`, `synthetic`) and `transitional`;
  an observed claim must also carry `datasetVersion`, `datasetChecksum`, and
  `configHash`, the last two as SHA-256 hex. An artifact with no block loads
  with `transitional: null` — unknown — which deployed profiles refuse and
  readiness reports as such. Eleven malformed-provenance cases are tested.
- **P2 — valid policies priced outside the trained domain with no signal.**
  Fixed by signalling rather than by widening the grid. The artifact records
  the grids it was fitted on; `/predict` now returns `extrapolated: true` when
  the window or threshold lies outside them (1–6 days, 1–9 mm, above 300 mm).
  Widening the grid was measured first: adding 1- and 3-day windows and 1- and
  5-mm thresholds moved the predicted trigger rate on the core grid from 0.101
  to 0.062–0.087 against 0.097 observed. A model with one wetness feature
  cannot fit both extremes, so the honest answer is a flag, not a worse model.
- **P2 — the gate could pass a per-region degradation.** Fixed in part. The
  metrics file now reports log-loss, Brier, and both trigger rates per region,
  for the new and the archived model. Tests require every region's predicted
  rate to be at least half the observed one, and the observed model to beat
  the synthetic one in every region with measurable risk. Doing that surfaced
  two limitations recorded below (Lima and Buenos Aires). Comparison against
  "the last approved observed model" is not yet possible because there is
  only one; the archive directory and the `previousModel` block are where it
  will go.
- **P3 — the region registry was read without validation.** Fixed.
  `app/data/regions.py` is the single loader: duplicate keys rejected, keys
  must already be canonical (`strip().lower()`) and within the on-chain byte
  budget, names and countries non-empty, coordinates finite and in range,
  schema version checked. Used by the fetcher, the gate, and the tests.
- **P3 — the gate retrained over the real artifacts and could recreate a
  missing one.** Fixed. `train_rainfall_model.py --check` compares what a run
  would write against the committed files and writes nothing; a missing file
  is a failure. The gate runs check mode and additionally asserts the files'
  bytes did not change across it. Producing an artifact is now only ever the
  deliberate, flagless invocation.

### Second review round

A second review of the hardened stage produced eight findings.

- **P1 — grid cells under-priced even with the loading.** Confirmed: 96 of
  448 holdout cells, 29 with a real sample; Buenos Aires at 14 days and 30 mm
  observed 23.7% against a 9.7% loaded premium. The cause was the model, not
  the gate: one mean-rainfall feature cannot place a desert and a pampa on
  the same line. Fixed by fitting one effect per region — expressible in the
  unchanged artifact contract as `regionRisk` with a unit coefficient — which
  cuts the under-priced sampled cells from 29 to 11, brings that Buenos Aires
  cell to 20.4% predicted, and improves the aggregate log-loss from 0.1823 to
  0.1727 while every region's loaded premium now covers its observed payouts.
  Per-cell metrics are reported with the worst named, and the acceptance
  policy is stated in the tests: region-level solvency as a requirement, a
  cell-level tripwire as a regression guard. Interactions (a threshold slope
  per region) are not expressible in the artifact and were not attempted.
- **P1 — settlement semantics not yet fixed by Stage 10.** Declined again
  for the same reason as the first round; the reviewer agrees it is a
  legitimate deferral. The one-day consistency between provider and quote
  was independently confirmed.
- **P2 — the release was not atomic across artifact and metrics.** Fixed.
  `release()` stages both files beside their destinations, fsyncs, loads the
  staged artifact exactly as the runtime would, and only then moves them into
  place — metrics first, then the artifact, so an interrupted release leaves
  the old, valid artifact loadable. A failing release leaves no staging file.
- **P2 — `stage7_check.py` still ran a destructive release.** Fixed: it runs
  `--check`, fails on a missing artifact, and asserts the bytes did not move.
- **P2 — an observed artifact could carry an empty source and be admitted.**
  Fixed at both ends. The dataset loader requires `source` to be an object
  with provider, product, URL, variable, units, timezone, and licence as
  non-empty strings — `[]` no longer reads as `{}` — and requires coordinates
  to be finite numbers in range. The artifact loader requires an observed
  block to carry `source` (with provider and URL) and a `dateRange` of
  calendar dates.
- **P2 — physically impossible values were accepted.** Fixed with a bound
  that has a physical meaning rather than a statistical one: 2,000 mm in a
  day, above the WMO 24-hour world record of 1,825 mm (Foc-Foc, La Réunion,
  1966), applied by the fetcher and the loader with the citation in the code.
- **P3 — parser edges and a fixed staging name.** Fixed: a huge JSON integer
  is a `RainfallDatasetError`/`FetchError` rather than an `OverflowError`, a
  non-object `daily_units` is a `FetchError`, and staging files are named per
  process so two refreshes cannot clobber each other.
- **P3 — documentation drift.** Fixed: the checksum recorded here is the one
  at the close of this round, and `requirements.txt` no longer names the
  removed synthetic build script.

### Third review round

A third review produced five findings. Two were about the model and were
measured before being answered; three were about the pipeline and were fixed.

- **P1 — the quote ignored the start date.** Confirmed, and the largest
  actuarial gap the stage had: Sevilla at 30 days and 20 mm observed 0.00 in
  April and 0.78 in November on the holdout and was priced identically for
  both, which a product sold by dates cannot survive — it would be bought only
  for the wet months. Fixed by fitting twelve monthly log-odds offsets per
  region (`seasonRisk`) on the residuals of the linear model, centred at zero,
  and applying them at quote time in proportion to the share of the window in
  each month. `PricingInputs` carries the start date; the runtime refuses to
  price a seasonal model without it. Holdout log-loss improved from 0.1727 to
  0.1628 on the previous dataset before anything else changed, and the
  by-start-month calibration for short windows now covers observed payouts in
  every month. A 365-day window sees almost no seasonal term, as it should.
- **P1 — 57% of the grid had no per-cell criterion.** Confirmed: the sample
  floor of fifty windows excluded every duration of sixty days and above,
  where the holdout offers 6–36 windows per cell, and 55 of the 66 point
  under-priced cells lived there — Valencia at 365 days and 30 mm observed
  6 of 6 against a loaded premium of 0.47. Two answers, both measured. The
  model side: the cloglog link, per-region threshold slopes, a
  threshold×duration interaction, and quadratic terms were each fitted and
  scored; none reached those cells and most made the aggregate worse. What
  did reach them is the **evidence floor**: the one-sided 95% lower confidence
  bound of each training cell's observed frequency, applied to every quote
  that dominates the cell (same region, at least as long, threshold at least
  as low) — a bound that holds because the true probability is monotone in
  both, and that twenty-four years support far better than a fitted slope.
  The criterion side: the sample floor is gone. Every cell is judged by
  whether the loaded premium falls below the exact Clopper–Pearson lower
  bound of its observed frequency, so six windows are judged by what six
  windows can prove (six of six proves 0.607, not 1.0). The acceptance bar is
  to stay within the number of flags chance alone would raise for a
  calibrated model — 30 for 448 cells at 95% — because zero is a promise no
  honest model can make about six years of weather. This release flags 6 (the
  previous observed one 16, the synthetic 167), all in Valencia and Sevilla
  at 90–365 days and 30–80 mm, where 2020–2025 was wetter than the training
  record the floor was built from; the report's risks name them. Long windows
  are additionally judged pooled by duration, where the sample is real, and
  every duration's loaded premium covers its observed payouts.
- **P2 — the refresh was frozen at 2024.** Fixed. The fetch window is now the
  thirty complete years ending at the most recent complete year at the time
  of the fetch; the dataset names its range in `datasetVersion` under a stable
  filename; the split is derived from the dataset (last six complete years
  held out); and the gate enforces a freshness policy — more than two complete
  years behind the latest fails it, with the refresh command in the message.
  The dataset was refreshed to 1996–2025 in this round, so the holdout is now
  2020–2025 and every archived model is rescored on it.
- **P2 — the release could publish metrics without the artifact.** Fixed. If
  the second rename fails, the previous metrics are restored, so the pair on
  disk stays a pair; a test injects the failure between the two renames. A
  power loss at exactly that instant is the one case a rollback cannot cover,
  and the gate catches it because the metrics would no longer match the
  artifact.
- **P3 — loader edges.** Fixed: `schemaVersion` must be an integer (`1.0` and
  `true` are refused), coordinate overflow is a `RainfallDatasetError`, and
  dates must be spelled `YYYY-MM-DD` in both the dataset and the artifact's
  `training.dateRange` — `fromisoformat` alone accepts `19950101`.

The runtime grew for the first time in this stage: `PricingInputs` carries a
start date, `assess_risk` applies the seasonal term and the evidence floor,
the artifact loader validates `seasonRisk` and `evidenceFloor`, and the
response carries `pricedFromEvidence`. Older artifacts — the archived v1 and
v2 — load and price without either term, which is how the comparison on the
shared holdout is possible.

### Declined, with reasons

- **P1 — metrics are calibrated against a settlement semantics Stage 10 has
  not fixed.** Correct, and already the first item under risks: the model
  scores "one callback per daily UTC precipitation sum" because that is the
  unit the data comes in. Defining the settlement rule is Stage 10's work,
  and the reconciliation this report asks for — compare the oracle's series
  against this dataset before trusting the calibration — is the handoff note
  below. Nothing in this stage can fix it without inventing the oracle.
- **P2 — versioning is not immutable and the artifact records no git
  commit.** The checksum is the immutable identity of both the dataset and
  the artifact; a version *name* is a label for humans. A refreshed dataset
  under the same name has a different checksum, a different `fetchedAt`, and
  produces an artifact with a different `datasetChecksum`, and the gate fails
  until both are committed together — so the change cannot be silent. A git
  commit hash inside the artifact is circular: the commit that contains the
  artifact cannot know its own hash. The trainer's own SHA-256 inside
  `configHash` is the non-circular equivalent, and it changes exactly when the
  training procedure does.

## Risks or pending items

- **Six cells are under-priced with confidence, all in Valencia and Sevilla
  at long windows.** Valencia at 365 days / 30 and 80 mm, 180 days / 30 and
  80 mm, 90 days / 80 mm, and Sevilla at 90 days / 30 mm: the holdout years
  2020–2025 were wetter at those extremes than the 1996–2019 record the
  evidence floor was built from (the 2024 Valencia DANA is in the holdout).
  Six flags against a chance allowance of 30 is within what a calibrated
  model would show, and the margins are small in four of the six, but the
  direction is consistent with a wetting trend at Mediterranean extremes
  that a stationary model cannot follow. The evidence floor will absorb it at
  the next refresh, when those years enter the training record; a trend term
  is the modelling step beyond that, and should wait for Stage 10's
  settlement data.
- **Lima is still over-predicted.** 0.015 predicted against 0.001 observed on
  the holdout — a buyer paying for risk that is not there once above the
  minimum premium. The ceiling of a model with one threshold slope for every
  region; a per-region slope was measured and did not pay for itself
  elsewhere.

- **Reanalysis is not a rain gauge.** ERA5 is a model constrained by
  observations at ~10 km; local convective extremes can be smoothed relative
  to what a station at the policy's location records. The oracle that settles
  a policy (Stage 10) will read some specific source, and the pricing data
  should be reconciled with that source once it exists. Until then, the
  model's probabilities are calibrated to ERA5's view of the trigger, not
  necessarily to the oracle's.
- **Eight regions, one point each.** A region is priced from a single
  coordinate. That is the registry's honest scope; expanding it is data work
  (register, refetch, retrain), and the gate will refuse a registry that
  disagrees with the dataset.
- **Unknown regions are priced at the mean risk.** Carried over from
  Stage 07 and now meaning the mean of the eight observed series. It remains
  a placeholder, not a risk assessment.
- **Stationarity is assumed.** The model is fitted on 1995-2018 and scored on
  2019-2024; both periods are in the past. A warming climate shifts extreme
  precipitation, and a model this simple has no term for that. The metrics
  file makes drift visible when the dataset is refreshed and the holdout
  moves; nothing yet acts on it.
- **Extreme thresholds are extrapolated.** Beyond roughly 120 mm/day the
  observed frequency is near zero for every region and the fit is governed
  by the log-threshold slope, not by counts. Quotes at those thresholds are
  the floor's business, as the floor test now documents.
- **No authentication and no rate limiting** — unchanged from Stage 07, and
  unchanged in urgency: Stage 09 defines the topology. `/predict` must not be
  exposed publicly before then.
- **A refreshed dataset changes the artifact.** By design — but it means a
  data refresh is a model release, with the same review a code change gets.
